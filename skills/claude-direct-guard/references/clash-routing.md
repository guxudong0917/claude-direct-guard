# Clash / Mihomo 分流：保留现有使用范围

## 随附规则

[examples/clash-verge-rules.yaml](../examples/clash-verge-rules.yaml) 来自用户本机现有的 Claude 专用规则扩展，共 22 条：20 条域名规则，加 2 条 IP 兜底。只保留分流指令，没有订阅、代理服务器地址、出口 IP、节点密码、控制器密钥或账号配置。

策略组名沿用 `🤖AI服务`。应用前确认目标订阅已经有这个组，并核对组内选择的实际节点；其他机器需要替换成自己现有的代理组名。示例不创建代理组、不提供节点，也不指定某个机场节点编号。

这份 YAML 的 `prepend / append / delete` 是 **Clash Verge Rev 的规则扩展格式**，应关联到要生效的订阅。不要当作完整订阅或全局 Merge 配置直接覆盖。其他 Mihomo 客户端应按其支持的规则格式适配，保留规则的顺序和含义。

## 分流和防直连分开配置

| 层次 | 做什么 | 何时起作用 |
|---|---|---|
| Clash 规则扩展 | 把匹配域名或目标网段送入选定代理组 | 规则模式下、连接被核心接管时 |
| 全局模式 | 被核心接管的流量按全局选择处理 | 不靠这份域名规则决定出口 |
| Windows 目标 IP 阻止 | 阻止指定网段的本机直接出站 | 规则及有效防火墙配置文件匹配时 |

代理规则命中某个组，不代表组内永远使用同一个出口 IP。自动测速、故障转移、上游分流和节点本身的地址变动都需要结合实际证据解释，不凭规则名认定固定出口。

这份现有分流示例的 IP 兜底为 `160.79.104.0/23` 与 `2607:6bc0::/48`。本案例的 Windows 防火墙后来经用户要求扩大到 `/21` 与 `/32`；这是不同层的两个配置，发布分流示例不擅自把它们改成同一范围。用户明确要求同步时再原地修改并核验。

默认不要为了使用这份规则而切换当前 Clash 模式、节点、TUN 或 DNS。用户要求调整分流时，按实际客户端版本找到关联扩展，先备份旧内容，给出最小差异；规则放在会提前命中的通用规则之前。保留其他站点的直连或代理规则，不增加整机 `MATCH` 强制代理，不修改默认出站策略。

## 共享域名与边界

示例里有 Sentry、Statsig、Datadog、Intercom、Fathom 等第三方域名，其中部分被多个产品共用。匹配这些域名会同时改变其他产品对应请求的代理路线；它们不是 Claude 独占的服务器名单。

**不要把这些共享域名解析出的 IP 自动加入 Windows 阻止列表，不要封锁整个 Cloudflare 等共享 CDN 网段。** 排查 ChatGPT 或其他网站异常时，先查看实际失败域名、路由和本轮改动。

这是用户环境中已经存在的规则集合，不宣称是官方完整清单或覆盖所有未来端点。缺少某条第三方监控规则不能直接推断封号；这份示例也没有配置 NTP 代理、改变系统时区或保证账号安全。

## 核验和回滚

- 检查 YAML 结构、代理组是否存在、关联订阅及扩展优先级，读取最终运行规则。可以用受信任的本机核心对隔离配置做语法检查；语法通过不等于流量已经按预期路由。
- 已获准进行连接验证时，查看核心连接记录中的命中规则与实际代理链。不要输出包含密钥的完整配置，不用真实登录会话主动制造直连请求。
- 验证 Claude 相关路由和用户要求保留的其他站点行为；新规则影响共享服务时只改对应规则。
- 出错时恢复本轮扩展备份，不重置全部 Clash 设置。修改分流不会自动创建、关闭或回滚系统防火墙规则。

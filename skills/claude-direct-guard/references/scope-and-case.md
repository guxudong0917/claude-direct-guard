官方文档说其所列固定地址不会不经通知变更，但不能把这句话解释成所有 Claude 网页关联服务的永久地址保证。第三方页面列出 AS399358；它的 Clash ASN 匹配不是 Windows 静态网段规则的自动更新机制。

IPv4 /23 覆盖 160.79.104.0–160.79.105.255，共 512 个地址；/21 覆盖 160.79.104.0–160.79.111.255，共 2048 个地址。后者包含前者，不能把官方入站与出站地址说成互不重叠。IPv6 /32 包含 /48，但更大不等于永远完整。

不默认扩成大网段。按当前用户的授权选择范围，核对新来源及可能影响。不要根据第三方文章的未经证实风控断言承诺防封号。

## 本案例学到的流程

用户最终选择仅按目标 IP 阻止直连，明确撤销整个 Chrome 依赖代理的方案；后来又明确批准从官方入站 /23、/48 扩大到 /21、/32。这是本次选择，不是所有用户的默认偏好。

当时两条规则的名称是：
- Codex-Claude-Destination-IPv4-20261030
- Codex-Claude-Destination-IPv6-20261030

这些名称可帮助原机器上的后续只读定位；在其他环境不要假定存在或机械沿用日期。最后一次案例核验为 2026-10-30 10:24:27（UTC−7）：两条规则仍在 ActiveStore、Enabled=True、Block、Outbound，地址为扩大的范围。该历史快照不能代替当前核验。

规则曾成功写入后消失。Windows 防火墙日志先记录修改程序为 SunloginClient.exe，后记录为微软签名有效的 Edge elevation_service.exe。用户自行卸载向日葵，之后同意临时停止 Edge 服务做对照，服务已在测试后恢复；较晚的只读检查又见服务 Stopped/Auto。没有证明 Edge 或向日葵普遍会删规则，也没有确认恶意软件、永久修复或后续服务停止的原因。

首次范围扩大命令错误地同时使用 Set-NetFirewallRule 的 -Name 与 -DisplayName，导致参数集冲突。更新标签需要 -NewDisplayName；先查本机命令参数，避免只做语法解析后就以为调用正确。

原临时服务测试的固定次数循环未包含查询耗时，超过预计 90 秒。之后的采样进程又在完整结束记录前终止。由此必须：使用实际时间预算，保证恢复，独立核验服务，并区分部分采样与完整测试。不要复制原测试脚本作为默认修复流程。

没有用用户的 Claude 登录会话主动测试直连。本案例最终验证了规则配置和短期保留，并未证明未来全部域名或所有接入路径永久不会直连。
